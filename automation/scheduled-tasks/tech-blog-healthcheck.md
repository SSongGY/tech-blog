## 1. 멈춘 회차 찾기 (매시)

`mcp__scheduled-tasks__list_task_runs`를 `tech-blog-daily`, `tech-blog-exam`,
`tech-blog-concept` **각각에 대해** `limit: 1`로 부른다.

가장 최근 실행이 아래 둘을 **모두** 만족하면 멈춘 것으로 본다.

- `status`가 `running`
- `last_activity_at`이 **25분** 넘게 그대로

**총 수행 시간으로 판단하지 않는다.** 정상 회차도 한 시간 넘게 돈다. 판단 기준은
**마지막 활동 시각**이다. 권한 프롬프트 앞에 서 있으면 이 값이 멈춰 있고,
일하고 있으면 계속 움직인다.

`running`인데 25분이 안 지났으면 **아무것도 하지 않고 조용히 끝낸다.** 정상이다.

## 2. 멈춘 회차 세우기 (매시)

멈춘 것을 찾았으면 `mcp__ccd_session_mgmt__stop_session`에 그 `session_id`를 준다.

**왜 세우는가.** 멈춘 회차는 사람이 승인할 때까지 영원히 서 있고, 그동안
**같은 작업의 다음 회차가 뜨지 못한다.** 한 회차가 막히면 그날 나머지가 전부
막힌다. 세우면 다음 차례가 제시각에 돈다.

세운 뒤 무엇이 남았는지 본다. **치우지는 않는다.**

```bash
python scripts/blog.py reset-writing --dry-run
python scripts/blog.py recent 3
```

보고에 이렇게 적는다.

- 어느 작업이 언제부터 멈춰 있었는지
- 세웠는지, 세우다 막혔는지
- 남은 뼈대 글과 `writing` 상태가 몇 개인지
- **치우는 명령 한 줄**: `python scripts/blog.py reset-writing`

### 보류로 빼는 이유

`reset-writing`은 그 주제를 `todo`가 아니라 **`blocked`(보류)** 로 바꾼다.
`todo`로 되돌리면 다음 무인 회차가 같은 주제를 다시 집고, 멈추게 만든 원인이
그대로면 **같은 자리에서 또 멈춘다.** 그러면 그 작업의 다음 회차들까지 계속 막힌다.

`blocked`인 주제는 `pick`·`pick-concepts`가 건너뛴다. 사람이 있을 때
`blog.py blocked`로 보고 `unblock`으로 풀어 다시 쓰게 한다. 보고에
**보류 몇 건이 쌓였는지** 적어 준다.

**직접 치우지 않는다.** 본문을 거의 다 써 놓고 멈췄을 수도 있어서, 버릴지 이어
쓸지는 사용자가 정한다.

`stop_session`이 권한에 막히면 **그 사실을 보고한다.** 억지로 돌아가지 않는다.

## 3. 실행 이력 확인 (오전 9시대)

오전 9시에 보는 시점에서는 **어제 12·15·17·19·23시**와 **오늘 2·4·7시** 회차가
모두 끝나 있어야 한다. 여덟 회차다.

`mcp__scheduled-tasks__list_scheduled_tasks`로 네 작업의 `enabled`·`nextRunAt`·`lastRunAt`을 본다.
**돌아온 taskId 목록과 `automation/scheduled-tasks/`의 파일 목록이 같은지도 본다.**
어느 한쪽에만 있으면 보고한다 — 작업을 지웠는데 사본이 남았거나, 사본만 있고
등록이 안 된 것이다. `tasks-diff`는 파일만 비교해서 이 경우를 잡지 못한다.

| 상황 | 판단 |
|---|---|
| 최근 회차가 전부 `succeeded` | 정상. 4번으로 |
| `status: failed` | **문제.** error 내용과 함께 보고 |
| `enabled: false` | **문제.** 작업이 꺼져 있다고 보고 |
| `tech-blog-daily` 마지막 실행이 **10시간** 넘게 없음 | **문제.** 회차를 건너뛰었다고 보고 |
| `exam`·`concept` 마지막 실행이 **15시간** 넘게 없음 | **문제.** 한 회차를 빠뜨린 것 |
| `nextRunAt`이 **모레 이후** | 확인 필요. 아래 주의를 먼저 읽는다 |

앱이 꺼져 있어 밀린 정도는 문제로 보지 않되, 위 한계를 넘으면 알린다.

**`nextRunAt` 하나로 판단하지 않는다.** 이 값은 이미 예약에 걸린 이번 차례가 아니라
**그 다음 차례**를 가리킬 때가 있다. 예약 시각 직전에 보면 내일 날짜로 보이므로,
그것만 보고 건너뛰었다고 판단하면 틀린다. **`lastRunAt`을 함께 본다.**
수동 실행도 그날의 예약 실행을 막지 않는다 — 둘 다 돈다.

## 4. 결과 확인 (오전 9시대)

다른 회차가 `running`이면 저장소 파일을 **읽기만 한다.**

```bash
python scripts/blog.py lint
python scripts/blog.py status
python scripts/blog.py exam-status
python scripts/blog.py tasks-diff
git log --oneline -14
git status --short
git rev-parse HEAD origin/main
```

확인할 것:

- `lint`에 `[NG]`가 있으면 **문제.** 어느 글의 어떤 항목인지 보고
- `status`에 **겹쳐 보이는 주제**가 나오면 알린다. 같은 글이 제목만 바꿔 두 번
  나가는 것을 막는 자리다
- `tasks-diff`가 `[다름]`·`[없음]`·`[사본없음]`을 내면 **문제.** 어느 작업인지 보고한다.
  **직접 맞추지 않는다** — 어느 쪽이 맞는지는 사용자가 정한다
- 워킹트리에 커밋 안 된 변경이 남아 있으면 **문제**
- `HEAD`와 `origin/main` 해시가 다르면 **푸시가 안 된 것.** 문제로 보고
- 최근 24시간 글이 **18편보다 적으면** 그 사실과 회차별 편수를 보고
- 트랙별 `todo` 잔량이 `low_watermark`(10) 이하인 트랙이 있으면 알려준다.
  **`basics`와 `linux`를 특히 본다** — 이 둘은 기출 회차가 채워 주지 않아 먼저 마른다
- `exam-status`에 `skipped`가 늘었으면 어느 문제를 왜 건너뛰었는지 알려준다
- `verification: manual-only` 글이 쌓여 있으면 편수를 알려준다

## 5. 보고 (오전 9시대)

**문제가 없으면 한 줄로 끝낸다.**
예: `정상 — 어제 12·15·17·19·23시와 오늘 2·4·7시 회차 모두 완료, 22편, lint 통과, 푸시됨`

여기에 쓴 글 제목만 덧붙인다. 사용자가 무엇이 쌓였는지 알 수 있게.

문제가 있을 때만 자세히 쓴다 — 무엇이 잘못됐는지, 마지막 정상 회차가 언제였는지,
확인해 볼 지점. 직접 고치지는 않는다.

## 하지 말 것

- **저장소를 고치지 않는다.** 커밋·푸시·파일 수정·`git add` 전부 금지
- **`reset-writing`을 `--dry-run` 없이 돌리지 않는다.** 치우는 판단은 사용자가 한다
- 스케줄 작업을 끄거나 고치지 않는다
- 글을 대신 써주지 않는다
- 원격 DB에 접속하지 않는다
- 멈추지 않은 회차를 세우지 않는다. 25분 기준을 지킨다

## 명령 실행 규칙

- **Bash 도구로 실행한다.** PowerShell 도구는 허용 규칙이 없어 전부 물어본다
- **`cd`로 작업 폴더를 옮기지 않는다.** 이미 저장소 루트에서 시작한다
- **명령 앞에 환경변수나 변수 할당을 붙이지 않는다.** 규칙이 맨 앞부분으로 맞춰 본다.
  `blog.py`는 인코딩을 스스로 맞추므로 `PYTHONUTF8=1`도 붙이지 않는다
- **`python -c`로 즉석 코드를 짜지 않는다.** 필요한 일은 `blog.py`에 명령이 있다
- `for`·`while` 루프, `sleep` 대기, `find -exec`, 서브셸, `xargs`,
  명령 치환 `$(...)` 을 쓰지 않는다. 다른 회차를 기다려야 하면
  `mcp__scheduled-tasks__list_task_runs` 를 다시 부른다
