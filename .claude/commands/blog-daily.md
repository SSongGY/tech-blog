이 저장소에서 이번 회차의 글 3편을 작성한다. 하루 2회(오전 7시·오후 7시) 돈다. [CLAUDE.md](../../CLAUDE.md)의 규칙을 그대로 따른다.

**타협 불가**: 검증되지 않은 문장은 쓰지 않는다 · 버전을 반드시 명시한다 ·
회사 내부 정보를 넣지 않는다.

## 0. 실행 환경 판별

먼저 무엇을 검증할 수 있는 환경인지 확인한다. 이후 판단이 여기에 달려 있다.

```bash
PYTHONUTF8=1 python scripts/blog.py env
```

**셸 `for` 루프로 직접 돌리지 않는다.** 복합 명령은 허용 규칙에 걸리지 않아
무인 회차가 권한 프롬프트 앞에서 멈춘다. 같은 이유로 `curl`·`find -exec`·서브셸도 쓰지 않는다.

해당 제품의 클라이언트가 있으면 제품 글도 `verification: executed`로 쓸 수 있다.
없으면 `manual-only`다.

## 1. 현황 확인

```bash
python scripts/blog.py status
python scripts/blog.py lint
```

- 트랙별 `todo`가 `low_watermark` 이하면 `topics/backlog.yaml`의 해당 트랙에 주제를 보충한다.
  `topics/published.md`로 중복을 먼저 확인하고, 각 주제에 `angle`과 `feature`를 채운다.
- 이전 날짜의 `verified: false` 글이 남아 있으면 그것부터 마무리한다.
- `verification: manual-only` 글이 있고 **지금 환경에 그 제품이 있으면**, 예제를 실제로 돌려
  출력을 채우고 `executed`로 승격한다. 새 글보다 이 승격이 우선이다.

## 2. 주제 선정

```bash
python scripts/blog.py pick
```

3편이 나온다. `DB문법 1 + 기술사 1`이 고정이고, 세 번째 자리는
`DB기능` / `리눅스` / `일반` 중 지금까지 가장 적게 쓴 트랙이 가져간다.
각 주제에 같은 `feature`로 쓴 글이 있으면 함께 표시된다.

**이 환경에서 검증할 수 없는 주제는 건너뛴다.** 필요한 런타임이 없으면 그 주제는 `todo`로
두고 `--<트랙> 3`으로 더 받아 실행 가능한 것을 고른다.
건너뛴 주제와 이유를 커밋 메시지에 한 줄 남긴다.

제품·기술사 주제는 실행 환경이 없어도 건너뛰지 않는다. `manual-only`로 쓴다.

## 3. 글마다 작성

```bash
python scripts/blog.py new <id> <영문-slug>
```

- `references/naming-conventions.md`에서 해당 언어의 명명 규칙을 확인한다
- **일반 트랙**: `code/`에 그 자체로 실행되는 예제를 작성하고 **실제로 실행한다.**
  난수는 시드를 고정한다. 출력이 기대와 다르면 글이 아니라 이해를 고친다.
  실행 결과를 본문에 그대로 싣는다. 측정값·실행계획·에러 메시지를 지어내지 않는다.
- **DB 문법 트랙**: SQLite로 돌려 출력을 확인한다. 입문자 대상이라 용어를 처음부터 설명한다
- **제품 트랙 (`manual-only`)**: 공식 매뉴얼에서 문법과 동작을 확인해 정리한다.
  **결과표·출력·측정값을 절대 지어내지 않는다.** 본문 상단에 "실행 검증 없음" 안내를 넣는다.
  근거를 못 찾은 동작은 쓰지 않는다. 단순 나열로 끝내지 말고 "어느 상황에 무엇을 쓰는가",
  "어디서 틀리기 쉬운가"를 넣는다.
- **기술사 트랙**: §7의 답안 구조를 따른다(정의 → 배경 → 구성요소 → 도식 → 비교 → 고려사항).
  정의는 표준 문서 근거로 쓰고, **항목 개수를 반드시 명시한다**. 근거 없는 수치를 쓰지 않는다.
  알고리즘·계산 주제(스케줄링, 페이지 교체, 정규화)는 **직접 계산해 검산하고** `executed`로 올린다.
- 본문에 사실 주장을 썼으면 그 주장도 따로 검증한다
  (예: "통계가 없으면 스킵 스캔이 안 나온다" → `ANALYZE` 유무로 직접 돌려 확인)
- **버전을 확인해 `environment`에 숫자까지 적는다.** 추정하지 않고 직접 뽑는다
- 예상과 달랐던 결과가 나오면 **그것을 글의 중심에 놓는다.** 가장 값이 나가는 부분이다
- **들어가며는 독자가 겪어봤을 법한 일상 장면으로 시작한다.**
  어쩌다 그 상황에 놓이는지 → 보통 택하는 비효율적인 방법 → 그게 왜 비싼지 순서
- **도식을 최소 1개, `fig/` 아래 SVG로 직접 작성한다.**
  - 먼저 **공식 문서에서 구조 근거를 찾는다.** 파일 포맷 명세, 매뉴얼, RFC, 논문 순으로 우선한다
  - 근거를 못 찾은 부분은 그리지 않는다. 내부 구조를 추측으로 그리지 않는다
  - **도식 바로 아래에 `> **출처**:` 줄을 넣는다.** 섹션 번호나 앵커까지 적는다.
    앵커가 실제로 있는지는 `blog.py check-links`가 확인한다
  - **기계 검사를 돌린다.** 캔버스 폭·배경 rect·글자 크기·박스 수·글자 넘침을 본다

    ```bash
    PYTHONUTF8=1 python scripts/blog.py check-svg posts/<...>/fig/<이름>.svg
    ```

    HTTP 서버를 띄우고 `curl`로 200을 받는 방식은 쓰지 않는다. 그건 파일이 서빙된다는
    뜻일 뿐, 글자가 잘렸는지와 무관하다. 검사용 HTML을 저장소에 만들지도 않는다
  - **겹침은 기계로 못 잡는다.** 사람이 볼 때 `file://`로 직접 열어 확인한다
  - **도식이 나타내는 의미가 맞는지 반드시 검산한다**
- `code/README.md`에 실행 방법과 바꿔볼 값을 적는다
- 본문 길이를 트랙 기준에 맞춘다 (`lint`가 트랙별로 센다)
- 검증이 끝나면 프론트매터를 `verified: true`로 바꾼다

### 같은 기능을 다른 제품에서 다룬 글이 있으면

`pick` 출력에 표시된다. 그 경우 **`## 다른 환경에서는`** 절을 넣어 비교한다.
문법 차이, 기본값 차이, 지원 여부 차이를 표로 정리하고 각각 어느 버전 기준인지 밝힌다.
**한쪽이 우월하다는 식으로 쓰지 않는다.** 설계 선택이 다른 것이다.

## 4. 상호 링크와 검사

```bash
python scripts/blog.py relink
python scripts/blog.py index
python scripts/blog.py lint
```

`relink`는 같은 `feature` 글끼리 서로를 가리키는 블록을 재생성한다. 기존 글에도 역링크가 생기므로
그 글들도 함께 커밋해야 한다.

`index`는 루트의 `POSTS.md`(글 목록 페이지)를 다시 만든다. 사용자가 이 파일로 글을 찾으므로
새 글을 쓸 때마다 반드시 갱신한다.

**`lint`를 통과하지 못한 글은 커밋하지 않는다.**


`relink`로 기존 글이 바뀐 경우는 별도 커밋으로 분리한다.

```
chore: <feature> 관련 글 상호 링크 갱신
```

마지막에 `git push`한다.

  기준을 어긴 3편보다 기준을 지킨 2편이 낫다. 채우려고 기준을 낮추지 않는다
- 건너뛴 주제와 이유
- `python scripts/blog.py status` / `lint` 결과

## 티스토리 발행

발행은 수동이다. 티스토리·네이버 모두 글쓰기 API가 종료되어 자동 발행이 불가능하다.
`python scripts/blog.py tistory <slug>`로 변환본과 발행 정보를 뽑아 사용자에게 안내한다.
변환본에는 도식 자리에 `[[도식 fig/....svg]]` 표식이 남으므로, 해당 SVG를 업로드해 그 자리에
넣어야 한다는 점을 파일 경로와 함께 알린다.
