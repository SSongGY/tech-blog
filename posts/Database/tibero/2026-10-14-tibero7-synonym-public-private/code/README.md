# 예제 코드 — Tibero 7 시노님

**아직 실행하지 않았다.** 글을 쓴 환경에 `tbsql`이 없어 Tibero에 붙을 수 없었다.
클라이언트가 있는 환경에서 이 스크립트를 돌려 출력을 채우고 글을 `executed`로 올린다.

빈 스키마에 표 두 개(`syn_src_orders`, `syn_local_orders`)를 만들고, 전용 시노님이
표와 이름을 나눠 쓰는지, 공용 시노님은 같은 이름으로도 만들어지는지, 그리고 스키마를
안 붙인 이름을 쳤을 때 표와 공용 시노님 중 무엇이 읽히는지를 차례로 친다.
끝에서 만든 객체를 전부 지우고 `user_objects`에 남은 것이 없는지 확인한다.

## 실행

```bash
tbsql -s <사용자>/<암호> @synonym_namespace.sql
```

6~11번은 `CREATE PUBLIC SYNONYM` · `DROP PUBLIC SYNONYM` 권한이 있어야 돈다.
없으면 전용 시노님 부분(2~5번)만 돌려도 네임스페이스 공유는 확인된다.

## 확인할 것

매뉴얼이 적어 두지 않았거나, 적혀 있어도 실제 코드를 모르는 항목이다.
돌린 뒤 글에 반영한다.

- **3번** — 같은 스키마에 있는 표 이름으로 전용 시노님을 만들 때 나오는 에러 코드.
  매뉴얼은 "하나의 네임스페이스 안에서 이름이 유일해야 한다"고만 적는다.
- **4번** — 대상이 없는 시노님의 생성이 정말 성공하는지, 그리고 조회할 때 나오는 코드.
  매뉴얼은 "접근하면 에러가 발생한다"고만 적고 코드를 적지 않는다.
- **7번** — 이 글의 핵심. 같은 이름의 표와 공용 시노님이 둘 다 있을 때 무엇이 읽히는지.
  매뉴얼의 탐색 과정은 ① 현재 사용자 스키마 → ② 공용 시노님 순서이므로 표가 읽혀야 한다.
  `'from syn_local_orders'`가 나오면 본문대로다.
- **9번** — 공용 시노님이 `ALL_SYNONYMS.OWNER`에 어떤 값으로 보이는지.
  매뉴얼은 이 값을 적어 두지 않았다.
- **10번** — 시노님이 시노님을 가리키는 체인이 몇 단계까지 따라가지는지.

## 바꿔 볼 값

- 7번 전에 `DROP TABLE syn_local_orders`를 넣고 다시 조회하면, ①에서 못 찾으니
  ②의 공용 시노님이 쓰여 `'from syn_src_orders'`가 나와야 한다. 탐색 순서를
  양쪽에서 확인하는 대조군이다.
- 6번의 공용 시노님을 다른 사용자로 접속해 조회하면, 그 사용자 스키마에는 같은 이름이
  없으므로 공용 시노님이 쓰인다. 다만 `syn_src_orders`에 `GRANT SELECT`가 없으면
  시노님 자체에는 권한이 없으므로 접근이 막힌다 — 이것도 같이 확인한다.
