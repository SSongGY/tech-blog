스키마와 데이터 — 아래 질의는 전부 이 표를 대상으로 한다
================================================================
[employee]  9행
  컬럼       | 타입    | 제약
  -----------+---------+---------
  id         | INTEGER | PK
  name       | TEXT    | NOT NULL
  title      | TEXT    | NOT NULL
  manager_id | INTEGER |

  id | name   | title      | manager_id
  ---+--------+------------+-----------
   1 | 김대표 | 사장       |       NULL
   2 | 이본부 | 개발본부장 |          1
   3 | 박본부 | 영업본부장 |          1
   4 | 최팀장 | 플랫폼팀장 |          2
   5 | 정팀장 | 데이터팀장 |          2
   6 | 한사원 | 플랫폼팀   |          4
   7 | 오사원 | 플랫폼팀   |          4
   8 | 서사원 | 데이터팀   |          5
   9 | 윤사원 | 영업1팀    |          3

== 1. 자기 조인으로는 한 단계씩만 내려간다 ==

[1-A 개발본부장(2)의 직속 부하]
  ('id', 'name', 'title')
  (4, '최팀장', '플랫폼팀장')
  (5, '정팀장', '데이터팀장')

[1-B 두 단계 아래까지 — 조인을 한 번 더 적어야 한다]
  ('id', 'name', 'title')
  (6, '한사원', '플랫폼팀')
  (7, '오사원', '플랫폼팀')
  (8, '서사원', '데이터팀')

== 2. 재귀 CTE — 깊이에 상관없이 전부 내려간다 ==

[2-A 개발본부장(2) 아래 전원, level 은 2 를 1 로 둔 깊이]
  ('level', 'id', 'name', 'title')
  (1, 2, '이본부', '개발본부장')
  (2, 5, '정팀장', '데이터팀장')
  (2, 4, '최팀장', '플랫폼팀장')
  (3, 8, '서사원', '데이터팀')
  (3, 7, '오사원', '플랫폼팀')
  (3, 6, '한사원', '플랫폼팀')

== 3. 위로 올라가기 — 한사원(6)의 보고 라인 ==

[3-A 상사 체인]
  ('hop', 'id', 'name', 'title')
  (0, 6, '한사원', '플랫폼팀')
  (1, 4, '최팀장', '플랫폼팀장')
  (2, 2, '이본부', '개발본부장')
  (3, 1, '김대표', '사장')

== 4. 경로 문자열 — 재귀 단계마다 이어 붙인다 ==

[4-A 사장부터 각 직원까지의 경로]
  ('level', 'path')
  (1, '김대표')
  (2, '김대표 > 박본부')
  (3, '김대표 > 박본부 > 윤사원')
  (2, '김대표 > 이본부')
  (3, '김대표 > 이본부 > 정팀장')
  (4, '김대표 > 이본부 > 정팀장 > 서사원')
  (3, '김대표 > 이본부 > 최팀장')
  (4, '김대표 > 이본부 > 최팀장 > 오사원')
  (4, '김대표 > 이본부 > 최팀장 > 한사원')

== 5. 꺼내는 순서 — 재귀 SELECT 의 ORDER BY 가 정한다 ==

[5-A ORDER BY 없음 (현재 구현은 FIFO — 문서가 순서를 보장하지 않는다)]
  ('level', 'name')
  (1, '김대표')
  (2, '박본부')
  (2, '이본부')
  (3, '윤사원')
  (3, '정팀장')
  (3, '최팀장')
  (4, '서사원')
  (4, '오사원')
  (4, '한사원')

[5-B ORDER BY o.level + 1 — 너비 우선]
  ('level', 'name')
  (1, '김대표')
  (2, '박본부')
  (2, '이본부')
  (3, '윤사원')
  (3, '정팀장')
  (3, '최팀장')
  (4, '서사원')
  (4, '오사원')
  (4, '한사원')

[5-C ORDER BY o.level + 1 DESC — 깊이 우선]
  ('level', 'name')
  (1, '김대표')
  (2, '박본부')
  (3, '윤사원')
  (2, '이본부')
  (3, '정팀장')
  (4, '서사원')
  (3, '최팀장')
  (4, '오사원')
  (4, '한사원')

== 6. 실행계획 ==
  QUERY PLAN
  |--CO-ROUTINE subordinate
  |  |--SETUP
  |  |  `--SEARCH employee USING INTEGER PRIMARY KEY (rowid=?)
  |  `--RECURSIVE STEP
  |     |--SCAN s
  |     |--BLOOM FILTER ON e (manager_id=?)
  |     `--SEARCH e USING AUTOMATIC COVERING INDEX (manager_id=?)
  `--SCAN subordinate

== 7. 재귀 SELECT 에 쓸 수 없는 것 ==

[7-A 집계 함수]
  -> OperationalError: recursive aggregate queries not supported

[7-B 재귀 표를 두 번 참조]
  -> OperationalError: multiple references to recursive table: t

== 8. 종료 조건을 빠뜨리면 ==

[8-A WHERE 없는 숫자 생성 — 끝나지 않아서 끊었다]
  -> OperationalError: interrupted  (VDBE 명령 200,000개에서 끊음)

[8-B 같은 질의에 LIMIT 10 — 재귀가 멈춘다]
  행 10개, VDBE 명령 179개 만에 끝남

== 9. 데이터에 순환이 생기면 — 사장(1)의 상사를 한사원(6)으로 ==

  ('id', 'name', 'manager_id')
  (6, '한사원', 4)
  (4, '최팀장', 2)
  (2, '이본부', 1)
  (1, '김대표', 6)
  (6, '한사원', 4)
  (4, '최팀장', 2)
  (2, '이본부', 1)
  (1, '김대표', 6)
  (6, '한사원', 4)
  (4, '최팀장', 2)
  (2, '이본부', 1)
  (1, '김대표', 6)

[9-B UNION — 똑같은 행은 큐에 다시 넣지 않아 스스로 멈춘다]
  ('id', 'name', 'manager_id')
  (6, '한사원', 4)
  (4, '최팀장', 2)
  (2, '이본부', 1)
  (1, '김대표', 6)

[9-C UNION 인데 hop 컬럼이 있으면 — 행이 매번 달라 멈추지 않는다]
  ('id', 'name', 'manager_id', 'hop')
