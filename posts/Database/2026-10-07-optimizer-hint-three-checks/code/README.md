# 예제 코드 — 옵티마이저 힌트를 쓰기 전에 확인할 3가지

외부 의존성 없다. 파이썬 표준 라이브러리 `sqlite3`로 메모리 DB에 주문 표 `orders`(100,000행)와
상품 표 `product`(4행)를 만든다. 난수 시드를 고정했으므로 같은 데이터가 매번 만들어진다.
`dbshow.py`는 표 정의와 데이터를 찍는 보조 모듈이다.

## 실행

```bash
python hint_three_checks.py
```

확인 환경: SQLite 3.49.1 (파이썬 내장) / Python 3.13.5 / Windows 11. 실행 기록은 `output.txt`.

## 각 장이 보는 것

| 장 | 확인하는 것 |
|---|---|
| 확인 1 | 낡은 통계로 고른 나쁜 계획을 `INDEXED BY`로 덮는 것과 `ANALYZE`로 고치는 것의 결과가 같다 |
| 확인 2 | 지금 데이터에 맞는 계획을 힌트로 못 박은 뒤 분포가 뒤집히면, 힌트 없는 질의는 계획을 바꾸고 힌트 질의는 느린 쪽에 남는다 |
| 확인 3 | 조건이 못 쓰는 인덱스를 `INDEXED BY`로 지정하면, 부분 인덱스 힌트에서 조건 값이 바뀌면, 인덱스 이름이 바뀌면 각각 무슨 일이 나는가. 통계 없는 새 인덱스, `NOT INDEXED`의 동작 |
| 덤 4 | 단항 `+`가 인덱스뿐 아니라 타입 친화도도 벗겨 `code = 5`의 결과가 바뀐다 |
| 덤 5 | `likelihood()`가 계획을 바꾸는지, 인덱스를 지워도 질의가 깨지지 않는지 |

실제 일의 양은 VDBE 명령 수로 센다(`set_progress_handler`를 명령 1개마다). 시간 중앙값은 참고용이다 —
진행 핸들러를 건 실행과 따로 7번 돌려 재므로 같은 질의라도 환경에 따라 흔들린다.

## 바꿔 볼 값

- `UPDATE ... WHERE order_id % 100 <> 0`의 `100`을 `10`으로 바꾸면 'DONE'이 90%가 된다. 확인 2의 격차가 줄어든다.
- 확인 2에서 `ANALYZE`를 빼면 확인 1과 같은 상황(낡은 통계)이 되어 2-c도 느린 계획을 고른다.
- 덤 4의 `product.code`를 `INTEGER`로 선언하면 4-a·4-b 결과가 같아진다 — 친화도가 둘 다 숫자이기 때문이다.
