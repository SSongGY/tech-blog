# 이벤트 소싱 복원 비용 — 측정 예제

계좌 20개 × 이벤트 2만 건, 모두 40만 건을 인메모리 SQLite 이벤트 저장소에 넣고
복원 비용이 어디서 늘고 무엇이 그것을 막는지 잰다. 표준 라이브러리만 쓴다.

## 실행

```bash
python replay_cost.py
```

## 무엇을 재는가

| 절 | 측정 | 보려는 것 |
|---|---|---|
| 1 | 스냅샷 없는 애그리거트 복원 | 이벤트당 비용이 일정한가 (= 총비용이 선형인가) |
| 2 | 1만 건마다 스냅샷을 둔 복원 | 복원 비용의 상한이 무엇으로 정해지는가 |
| 3 | 읽기 모델 전체 재구축 | 스냅샷이 이 경로를 줄여 주는가 |
| 4 | 업캐스팅을 끼운 복원 | 스키마 버전 분기가 복원마다 얼마를 더 먹는가 |

각 측정은 3회 돌려 **최솟값**을 쓴다. 다른 프로세스의 간섭은 시간을 늘리기만 하므로
최솟값이 그 환경의 하한에 가장 가깝다.

## 바꿔 볼 값

- `SNAPSHOT_EVERY` 를 1,000이나 50,000으로 바꿔 본다. 복원 시간의 상한이 같이 움직인다.
- `EVENTS_PER_AGGREGATE` 를 늘려 본다. 1절의 이벤트당 비용은 거의 그대로이고
  총 복원 시간만 비례해 늘어난다.
- `apply_event` 안에서 무거운 계산을 하면 이벤트당 비용이 올라간다. 복원 비용은
  이벤트 수와 이벤트 하나의 처리 비용의 곱이다.
