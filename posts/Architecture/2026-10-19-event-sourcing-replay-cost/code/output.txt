========================================================================
1. 스냅샷 없는 복원 — 이벤트 수를 늘려 가며
========================================================================
  적용 이벤트 수   복원 시간(ms)   이벤트당(마이크로초)   잔액
           2,500             3.3                  1.335   250,000
           5,000             6.5                  1.302   500,000
          10,000            12.8                  1.276   1,000,000
          20,000            26.6                  1.330   2,000,000

========================================================================
2. 10,000건마다 스냅샷을 둔 복원
========================================================================
  만들어진 스냅샷  40개
  복원 지점 버전   복원 시간(ms)   스냅샷 뒤로 적용한 이벤트 수
          10,001             0.0                             1
          12,500             3.3                         2,500
          15,000             6.6                         5,000
          19,999            13.1                         9,999

  최악의 지점(19,999)  스냅샷 없음 26.7ms → 있음 13.3ms (2.0배)

========================================================================
3. 읽기 모델 재구축 — 스냅샷이 줄여 주는가
========================================================================
  저장소 전체 이벤트  400,000건
  보관 중인 스냅샷    40개
  재구축이 읽은 이벤트 400,000건  (= 전체의 100%)
  재구축 시간         1,474.6ms
  살아난 계좌 수      20개
  → 스냅샷 40개가 있어도 읽은 건수가 줄지 않는다. 이 경로의 입력은
     애그리거트의 현재 상태가 아니라 '모든 이벤트의 순서'이기 때문이다.

========================================================================
4. 이벤트 스키마가 바뀐 뒤 — 업캐스터는 영구 부채다
========================================================================
  acct-legacy 의 이벤트 (v1 2건 + v2 1건)
    v1  version=1  {"amount_str": "500"}
    v1  version=2  {"amount_str": "200"}
    v2  version=3  {"amount": 300}

  업캐스터 없이 복원: KeyError 'amount' — 옛 이벤트를 해석하지 못한다
  업캐스터를 끼운 복원: 잔액 600 (500 - 200 + 300 = 600 과 일치)
  → 이벤트는 불변이라 v1 레코드는 지워지지 않는다. v1 을 아는 코드는
     그 이벤트가 저장소에 남아 있는 동안 계속 유지해야 한다.

========================================================================
5. 이 측정의 잡음 폭 — 위 시간들을 어느 자리까지 믿을 수 있는가
========================================================================
  1절의 20,000건 복원을 맨 끝에서 다시 재면  71.2ms
  → 시간은 이만큼 흔들린다. 구조적 결과(이벤트당 비용이 일정하다,
     스냅샷이 꼬리 길이를 제한한다, 재구축이 전부를 읽는다)만 글에 쓴다.
