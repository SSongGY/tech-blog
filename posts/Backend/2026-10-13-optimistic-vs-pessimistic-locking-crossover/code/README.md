# 낙관적 잠금과 비관적 잠금 비교 예제

두 방식의 **비용 구조**를 같은 작업량으로 재는 모형이다. DB 벤치마크가 아니다.
저장소는 프로세스 안의 배열이고, 행 단위 원자적 갱신은 행마다 둔 자물쇠로 흉내 낸다.
읽고 쓰는 사이의 `sleep` 이 DB 왕복과 애플리케이션 처리에 해당한다.

외부 의존성이 없고 파이썬 표준 라이브러리만 쓴다. 한 번 도는 데 1~2분 걸린다.

## 실행

```bash
python locking_crossover.py
```

## 파일

| 파일 | 내용 |
|---|---|
| `locking_crossover.py` | 본문에 실린 네 장면을 순서대로 실행한다 |
| `output.txt` | 실제로 돌린 기록. 본문의 수치는 전부 여기서 가져왔다 |

## 바꿔 볼 값

- `POOL` 자리의 `demo_bounded_pool(4)` 를 `8`, `12` 로 올려 본다. 풀이 스레드 수에
  가까워질수록 역전이 사라진다. 재시도가 자원을 먹지 않으면 벽시계로는 티가 안 난다.
- `WORK_SECONDS` 를 `0.01` 로 늘리면 한 번의 헛시도가 비싸져 낙관적 쪽이 불리해진다.
  읽고 쓰는 사이가 길수록 낙관적 잠금은 손해다.
- `ROWS` 를 `8` 로 줄이면 '핫 로우 0%' 줄에서도 충돌이 생긴다. 충돌률은 핫 로우뿐
  아니라 **전체 행 수 대비 동시 작업자 수**로도 올라간다.
- `REPEATS` 를 늘리면 수치가 안정된다. 측정 시간은 그만큼 늘어난다.

## 주의

벽시계 수치는 이 기계와 이 파이썬 판에서 나온 값이다. 다른 곳에서는 절대값이 달라진다.
**재시도 횟수와 헛시도 횟수는 작업 목록이 같으면 구조적으로 같은 범위로 나온다** —
글에서 기대야 할 것은 이쪽이다.
